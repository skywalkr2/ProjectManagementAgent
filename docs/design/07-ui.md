# Part 7. UI specification (React)

## 7.0 Principles

- **A queue first.** The PM's day is a list of decisions. The home screen is **Today** (7.7): one ranked list, each line
  actionable where it stands, with its detail beside it and the day's context in a rail. Panels are filtered views of the
  same items, reached from Today or the sidebar.
- **Use the whole screen.** The app fills the window at every size and adds panes as the window grows (7.13). Only running
  prose is limited in width.
- **Never wider than the window** (owner, 2026-10-16: "the screen is bigger than my screen requiring scroll bars, that
  shoudl never be"). No screen scrolls sideways at any window width: columns wrap, stack or shrink, and long words break.
  Only a board with more columns than fit (Stages past about six) scrolls inside its own frame, never the page. A browser
  test checks every main screen at phone, laptop and wide widths.
- **Never raw data on screen** (B-6b). No title or line shows a data structure: a brace or bracket opening on a quote, a flow
  mapping (`{name: Launch}`) or a quoted key. Server text is checked by the wording check (`api/screen_text.py`), and the
  wording sheet by a test with the same rule (`web/src/lib/raw-data.ts`); a placeholder such as `{name}` and a quoted sentence
  are not data. `tests/test_screen_text.py`, `web/src/lib/raw-data.test.ts`, `web/src/wording/wording.test.ts`.
- **One primary action per row, always in the same place.** Other actions go in the row's "…" menu. The primary action is the
  likeliest next step for that row's state (Looks good, Copy, Answer, Approve, Pick an owner).
- **The cursor starts where you type** (owner, 2026-10-12). When a screen, step, form or dialog opens, the cursor is in
  its first main field; a screen with no field puts it on its heading, for a keyboard or screen reader. Nothing is
  focused that only looks selected. Shortcut keys never act while the cursor is in a field. *Built so far:* every dialog
  and drawer starts the cursor in its first field, or on its heading when it has none, and a field that arrives late takes it
  from the heading until the person moves it themselves (`ModalPanel`, `Drawer`, `web/src/lib/cursor.ts`); a source's form, a
  data file's form, the "ask someone else" form, the widen form and a record's first person field start in their first field;
  a screen changed to by a link puts the cursor in its first field (Settings, Quality) or on its heading, with one browser
  check for each main screen (`web/e2e/shell.spec.ts`). A page load itself takes no focus (`App.test.tsx`), as designed.
  `web/src/lib/cursor.test.tsx`, `ModalPanel.test.tsx`, `Drawer.test.tsx`, `AddFile.test.tsx`, `Sources.test.tsx`,
  `DataForms.test.tsx`, `ChangeThis.test.tsx`, `SourceLimit.test.tsx`, `RecordPage.test.tsx`.
- **Pick, don't type.** A field with a known set of values is a list to pick from: time zones, people, projects, value
  lists (5.4), accounts, models, folders, languages (owner, 2026-10-12, 2026-10-16: "the language setting should be a
  dropdown"). A typed box is for what only the person can say: a name, a note. A setting names its list (`choices`), so
  Settings and the walkthrough show the same list; a language is shown by its name in the browser's language and stored as
  its tag (the list offers only languages the app reads notes in, and its label says it is how the assistant writes, not
  the screens' language), and a project's language list starts with "Same as <the language it inherits>".
- **A secret is typed, not "set up somewhere else"** (owner, 2026-10-16). A password, key or private address is a password box
  on a local app: the app keeps it on this computer and the setting holds only where. "Where it is kept instead" is the second
  choice; a kept one reads "Kept on this computer" with Replace; a hosted app offers only where it is kept (4.0, 4.24).
  Built for a source's form, a read token, each key an add-on declares (its Settings section and its row on Add-ons) and the
  backup key (Backups and sync, with its warning and "Make one for me", the made key shown once to copy); the settings rows that
  hold those references are not listed twice (`web/src/components/KeptSecrets.test.tsx`).
- **Undo instead of "are you sure?".** The ledger makes almost everything reversible (6.7), so reversible actions happen at
  once with a toast ("Closed 3 actions · Undo"). Confirmation is only for what can't be undone: sending, publishing, posting.
- **Keyboard first, touch friendly.** Everything is reachable by keyboard (7.10); everything also works on a phone (7.1).
- **Edit in place.** A question, message or draft can be edited where it is shown, then approved; the PM's version is what's
  approved (content hash, 6.12) and the edit is a quality signal (6.20).
- **Show why.** Every claim the assistant made shows its evidence ("because: '...'"), and opening it shows the source with that
  passage highlighted (6.7).
- **Nothing moves under the PM.** New items arriving while the PM reads appear as "3 new · Show" at the top, never by pushing
  rows around.
- **Plain words.** Every label, message and empty state comes from one **wording sheet** (a string table, overridable by
  `config/ui.yaml` and translatable later). Internal terms (changeset, op, tier, held, ledger) never reach the screen; the sheet
  maps them to plain words ("what the assistant did", "waiting for you"). One word per idea: **Follow-ups** for what goes to
  people and what waits on them; **Needs you** for Today's queue and **Waiting for you** for a held item; **From outside · not
  instructions** for untrusted content. No command line, file name, config key path or `env:` reference shows on the
  default path; each is replaced by a button that does the step, or sits behind Details.

## 7.1 Shell and layout

One shell for every view: a one-row header across the top, a sidebar on the left, and the content area that fills the rest
of the window (7.13). The header and sidebar never move or change size when the view changes; only the content area does.
There is **no footer and no banner** above the content.

**The header** is one row, 56px (48px on a phone), at every width, and never wraps. From 1440px the assistant's line sits
beside the status chip; below 1440px (and on a phone) the assistant's state is a section of the status chip's popover
instead, so the row keeps its room. The workspace's name keeps its room before the Ask field gives any up (Ask shrinks
first, down to a small field), and the Ask field is an icon below 1024px. Left to right:
- The brand: the logo (`ui.brand.logo`, or a monogram from the workspace name) and the workspace name. Selecting it opens
  Today.
- A **Demo** chip when the app runs a demo workspace.
- **Ask** (6.25) as a search-style field with its `/` hint; on a phone it moves to the bottom bar.
- The **status chip**: one dot and a few words for the worst current state (all good "Live"; then, in order, Offline,
  Restart to finish, Backup needed, Spend near today's limit). Once a backup has succeeded the chip keeps its age beside the
  word ("Live · Backed up 3 h ago", or "Backup needed · Last backup 4 days ago" when overdue; a phone shows the word only,
  and the chip's name says both). It opens a popover listing every state with its action: the
  last and next check, Refresh, the backup's age and Back up now (4.15), today's AI spend, the Jobs that are running, the Log,
  and Restart now when a change waits for one (the restart rule: the app never restarts on its own).
- The **assistant's line**, beside the status chip from 1440px: the assistant's name, an icon and a few words. When
  nothing is wrong: "Assistant ✓ last run 9:42" (the time on the person's own clock, with the day when it was not today;
  "no runs yet" before the first). It is amber with a warning icon when work is held up by a state the chip knows (waiting
  for the network, a restart to finish or restarting, an account paused until its limit resets, no AI account yet) and red
  with a cross icon when the assistant can't do its work (its account can't be used, or its last run failed); the words say
  which, so status is never by color alone. A phone, and any window under 1440px, shows no assistant line in the header (a phone only the logo, the status chip and the
  avatar, with the workspace's name as the logo link's name); the assistant's state is a section of the status chip's popover
  there (the UI designer's "Also seen" table and re-review 3.7; **built:** `web/src/shell/Header.test.tsx`). It opens a popover with
  today's runs per account (count, and how many failed), what waits for the assistant (count and since when the oldest
  waits) and, per kind of work, the order its accounts are tried in. Accounts are shown by their own names in the settings,
  never a model's or a vendor's name. The line comes from `GET /api/status` (`assistant`), which reads only today's runs
  and the newest few, and counts no call that found no network. **Built:** `web/src/shell/Header.test.tsx`; the layout below
  1440px (one row, every control inside the window, the workspace's name whole, the assistant's state in the chip's popover
  with today's runs and what waits) is checked in a browser from 800 to 1300px (`web/e2e/shell.spec.ts`, "the header is one
  row"; written, not run).
- **Missed one** (6.32): a quiet button with its words, never a bare icon (re-review 3.7), opening the one-field form. It is
  shown once there is anything the assistant could have missed: once something has been handed in or read, so that What
  changed holds a row. On a new workspace the header and the phone's More sheet do not offer it (B-8, R4).
  `web/src/shell/Header.test.tsx`.
- **The workspace's name** is read again after any saved change, so a new name shows in the header and the page title at once,
  in the walkthrough or in Settings, with no reload (`web/src/App.test.tsx`).
- **Your pages** (B-6b): when the list in Settings (`ui.links`: a name and a web address each, up to twelve, edited in the Appearance
  section of Settings) isn't empty, **Your pages** is the first group of the person's menu (below), not a button of its own
  (re-review 3.7); each entry opens in a new tab, and an entry that isn't a web
  address is refused when it is saved and never opened. A change in Settings shows at once. `tests/test_header_links.py`,
  `web/src/shell/HeaderLinks.test.tsx`, `web/src/shell/Header.test.tsx`, `web/src/components/PageLinks.test.tsx`.
- **Hand something in**: the one primary button in the header, with a "+" icon.
- **Help**: an icon button for the shortcuts sheet, the setup guide, Send feedback and the version. Send feedback can
  add the last problems (owner, 2026-10-21; *built, B-11c*): each failed AI call, account check, connector read or
  server error from the last days (`ui.feedback_problem_days`), with when, the task kind, the account's service and
  program version, the request's exact parameters, the status code, the error kind and the service's own error text.
  Never the packet, mail, notes or any record's content; keys, tokens and addresses are masked. The person sees the
  whole email before it leaves, and the app still sends nothing itself.
- The person's initials, which open the **user menu**: Your pages when there are any, then theme (System, Light, Dark),
  density (Comfortable, Compact) and sign out when signed in.

The date and the number of things that need the PM sit in Today's own heading (7.7), not the header.

**The sidebar** lists the views, each with an icon, a label and a count where the count is useful:

| Group | Views |
|---|---|
| (top) | **Today** with its count |
| **Work** | What changed (7.3), Follow-ups (7.5), To-dos and questions (7.5), Waiting to go out (7.4), Stages; plugin work panels below these |
| **Records** | Projects (the portfolio table), People, Files; plugin record panels below these |
| (bottom) | Connections, Add-ons, Settings (7.9) |

- Every entry is a real link (`#work/stages`), so a view can be bookmarked, opened in a new tab and reached with Back.
- The sidebar is 232px with labels from 1280px; at 1024–1279px it is a 64px icon rail with a tooltip per icon, and the person
  can collapse or pin it at any width (remembered on this device).
- **Navigation budget.** The groups and the bottom entries are fixed. A plugin adds entries only *under* Work or Records
  (its panel's `tab`: `work` lists under Work, `people` under Records, `settings` in Settings' section list, `today` in Today's
  rail), and `config/ui.yaml` may reorder or hide them. Adding plugins never adds a top-level entry, so the shell never
  overflows. Admin pages (the assistant's queue, Quality 6.20, Rules 6.21, Security) are sections of Settings.
- The setup guide (7.8) is reached from the setup line on Today and from Help, not from the sidebar.

**On a phone** (below 640px):
- The sidebar becomes a **bottom bar**: Today · Work · **+** (Hand something in) · Ask · More. More lists the Records and
  bottom entries.
- Today shows the queue first; the rail's panels follow, collapsed to one line when empty.
- Each Work list opens one item at a time in a **review mode**: the item, its evidence and source, then Looks good, Send back
  and Next, full width at the bottom. No sideways scrolling and no menu needed to finish a review. **Built for What changed**
  (`web/src/components/ReviewMode.tsx`; tests: `web/src/components/WhatChanged.test.tsx`, "review mode on a phone"): a button
  "Review one at a time" starts it on the items waiting for a look; the three buttons press the item's own actions, so what
  they do and record is what the row's own buttons do; an approved item gives way to the next, and when none is left it says
  so with one button back to the list. *Not yet:* the other Work lists use it as they become list \| detail.
- Primary actions are full width only inside an open item. Toasts sit above the bottom bar.
- The tasks that matter most are first class: review and approve or send back, copy a message, answer a decision, hand
  something in (paste, or share text to the app). Installable on the home screen as a web app is a version 1 item.

**Where panels come from.** Views and their panels come from a **panel registry**: the core registers its panels, plugins
register theirs (7.2), and `config/ui.yaml` may reorder or hide them. The Projects view is the portfolio health table grouped
by the configured grouping; each project opens to its record page (7.14) with its RAID (risks, issues, assumptions,
dependencies, decisions) as configured in `config/raid.yaml`; plugins add sections.

## 7.2 Plugin panels

Plugins describe panels declaratively, so most need no front-end code and every one looks and behaves like the core:

```yaml
panel: personal-projects/goals
title: Goals
tab: work
source: {record_type: personal-projects/goal, filter: {status: open}}
view: table                                   # list, table, board, form, detail or compare
columns: [title, project, due, status]
primary_action: personal-projects/goal.update # the one action shown on the row
row_actions: [personal-projects/goal.close]   # the rest, in the row's menu; each runs as an op through the applier
```

Besides list, table, board, form and detail, the core offers a **compare** view for versions of a `long_text` field that any
panel can use: two-way (a pending draft or proposal against the current version) and three-way (base, current and handed
back, when the base moved after a working copy went out). It reuses the diff rendering of 7.4 (marks and screen-reader labels,
never color alone), moves change by change from the keyboard, and lets the person accept or reject each passage, or pick a
side in three-way; the choices submit one `text.accept` (6.7). The plugin names the field and the pending version; it writes no
diff or front-end code.

The panel spec is itself a JSON Schema, so a plugin's panels are validated like the rest of its manifest. Row actions and forms
submit ops, so plugin UI can't bypass validation, tiers or the ledger. A bundled plugin that needs more may ship a React
component, registered at build time against the same panel interface. Loading plugin components at runtime waits for a real
need.

## 7.3 What changed (one list for incoming changes and the assistant's work)

- One row per incoming change (source tag, linked title, state pill). The assistant's work for that change is nested inside
  ("What the assistant did (N)"), each item with its evidence line, next to "Show the change" (word-level diff). Details open by
  expanding the row, not in tooltips.
- One row per piece of the assistant's own work that didn't come from a change (requests, answers), tagged with the
  assistant's name. Automation problems are not here; they live on their own cards (6.13).
- **Primary action by state:** new change: Process with the assistant; reviewed: **Looks good** (closes the change and files
  its work); auto-closed: This is ours. In the menu: Done, Ignore, **Send back**, Undo, Take a closer look. Send back
  opens in the inspector (or a small anchored dialog) with the note focused, a checkbox "Undo what the assistant did first"
  (on by default) and the Send back button in view without scrolling; `s` opens it. The note's box is at most the 72ch
  measure wide, and the Send back button, while off for want of a note, says "Write what to do differently first."
  (re-review 3.13; `web/src/components/SmallPoints.test.tsx`).
- **Automation problems** (above What changed when any are open): one card per problem, saying what happened and what the
  cockpit is doing about it; primary action Draft a report, menu Dismiss.
- Filter: Needs attention, Processed, With the assistant, The assistant's own work, Done, Auto-closed, Ignored, All.
  "All looks good" for the reviewed rows shown, with an undo toast.
- **"To send" on an action's row.** An open action whose owner, someone other than the person, hasn't been told about it (or was
  told something since changed, 6.10) says **To send** in its meta line, in What changed and in To-dos and questions; telling
  the owner (Mark sent) takes it away, and changing the action's words brings it back. Someone the person only watches or
  reports to never gets it. **Built:** `tests/test_to_send_marker.py`, `web/src/components/OpenItems.test.tsx`,
  `web/src/components/WhatChanged.test.tsx`. What changed is list | detail (7.13), below.
- **The list is one line per change, the chosen change is in the detail** (re-review 3.6, list | detail of 7.13): a line has the
  state, the title, one line of what was done, its one primary action and the rest in its menu; what is being learned from it
  and the drafts and files it made stay on the line. Choosing a line (a click, Enter) shows the whole change in the detail
  pane beside the list from 1024px, as a drawer below that: the source with highlights, what the assistant did with its
  evidence, the second opinion and what it followed, the held questions, Looks good, Send back and Undo, and the same
  menu. As the list opens beside the pane the first change is chosen, or the first one that holds a question for the person,
  so none sits unseen over an unanswered question; below 1024px nothing opens until it is chosen. Up and Down move the choice
  with the cursor, Enter on a line moves the cursor into the detail, Escape closes the detail and puts the cursor back on its
  line; a change that is approved leaves the list and the next one is chosen. A menu item that needs a form (Send back with
  a note, the other account for a refused request) chooses the change and opens the form in the detail. A to-do's
  owner, the day and who it was promised to are **one meta line** ("Theo Brandt · due Fri, Oct 16 · promised to no one", and
  how it is known when that is on file), each part a button that opens a small popover with its list or date picker (the
  cursor starts in it, Escape closes it and the part gets the cursor back); picking applies it as the person's own
  correction with Undo (6.33). There are no stacked "Change" links. **Built so far:**
  `web/src/components/WhatChangedFold.test.tsx`; **list | detail built:** `web/src/components/WhatChangedListDetail.test.tsx`
  (one line per change, the first or the asking change chosen, Up, Down, Enter and Escape, every action from the detail, a
  drawer below 1024px), `web/src/lib/list-choice.ts` (the choice shared with Follow-ups); the browser tests are written, not
  yet run.

## 7.4 Waiting to go out

- Every draft for every channel in one list, grouped by channel. "Review changes" runs the dry run.
- Per draft: checkbox, title (left-aligned, wraps beside the checkbox), tags (new, dashboard view, wording check, scheduled,
  "built from outside content"), and a plain-words count ("3 changed, 2 added, 1 removed, 1 moved"). Primary action Approve;
  the draft can be edited in place first.
- Each channel's output type picks its preview. Pages: inline word-level diff by default, side by side as an option (version
  1); removed text is struck through **and** marked, added text underlined **and** marked, with screen-reader labels ("removed",
  "added"), never color alone; a mostly rewritten line shows old then new in full; small unchanged bits between changes fold
  into the change so phrases read old-then-new; table rows show cells joined cleanly with empty cells as "—"; a row that only
  moved shows once with a moved mark; a moved row whose cells changed shows as one in-place change. Short posts and messages:
  the full text as it will appear, with the channel's limits and a character count.
- **A format-only difference never appears here.** When the only difference left after a publish is formatting, that is an
  automation problem (6.3), not a draft, so nobody is asked to approve a no-op.
- Sending is the one place that confirms: a send message is required where the channel records one; sending a subset warns if
  a roll-up includes unticked drafts' changes. Success notes fade; errors stay with the offending lines and an "Ask the
  assistant to reword" button.
- **Built (B-6b), the empty state:** nothing is sent or published by the product yet (6.3, 6.12), so the screen says what will
  wait here, that nothing leaves without approval of its exact content, and how a message leaves in the meantime (copied from
  Follow-ups, sent by the person, marked sent), with the two ways on. The list, the previews and Approve come with the
  publisher. `web/src/components/WaitingToGoOut.test.tsx`.

## 7.5 Follow-ups

- **Filter:** "To send" (default), "Later" and "Waiting on them", styled like What changed's filter.
- **Later** (*phase B*): questions and action notices held for a meeting or the next weekly note (the question's `batch`,
  6.8), per person and collapsed, so To send stays honest. "Hold for later" is in a line's menu; "Send now" brings it back.
  With the project management pack's meetings, "Hold for <meeting>" puts it on that meeting's agenda. Items already sent or told show
  only under Waiting on them. **Built (phase B-6a):** a question held for a calendar entry, a series (its first instance
  on or after the day it was held, so it stays out of Later once that day has come) or a day (`Question.held_for`) is in
  Later and out of To send, the message and the Today send line until that day, when it is to send like any other; a moved
  meeting moves the day. "Hold for later…" is in the card's menu (the card's list has no per-item buttons) and asks which
  question and what to hold it for, from the calendar's meetings or a day; "Send now" is in the question's menu in Later;
  both act at once with Undo. Holding for the next weekly note (the question's `batch`) is *not built*. **Built (S1-2):**
  "Hold this message for later…" (offered when a message has more than one question to send) holds all of its questions
  for one meeting or day in one change, each by its own `held_for`; they come back numbered as before and Undo restores
  each. A to-do told in the message has no hold of this kind and stays to send.
  `tests/test_followups_later.py`, `web/src/components/FollowUps.test.tsx`.
- **To send, by person:** "You" first (decisions with Answer; your action items), then everyone with something still to send,
  A to Z, one card per person. Only people in the tracked area and domain contacts get a card; a contact's cross-domain
  questions are grouped under the domain's name. Header: the name, "N to send" and **Review & copy** (primary), plus **Send** when the
  person has a channel configured in `how_to_reach` (it creates a draft that waits for approval like any other). Review &
  copy (and `c` on a collapsed card) opens the message first: text never reaches the clipboard unless the message it copies
  is on screen at that moment. Opened, the
  card has "In this message" (a plain list of what is still to send, with project and due date, no per-item buttons), then the
  message box and Copy.
- **Copy, then Mark sent** (two steps). Copy shows the message it will copy, editable in place, and puts it on the clipboard
  only; nothing is recorded ("Copied" confirms). After a successful copy the card's primary action and the button under the
  box become **Mark sent**, which records the box's text as sent and shows an Undo toast ("Marked as sent to Ines"); the
  items then move to Waiting on them. The "copied" state lives in the component only. The card's menu always offers Mark sent,
  so it can be done after a reload or after sending some other way. The message has a greeting with first name, questions
  first (numbered when several), then "Action items with you:" as a list with project and due date, then one closing line, for
  items still to send only. No title-then-same-text repetition. If the browser blocks the copy, nothing changes and Copy stays.
  *Built (B-6a):* Copy on a closed card (the button, or `c`) opens the message with the cursor in it and copies nothing; the
  next Copy, with the message on screen, is the one that copies (`web/src/components/FollowUps.test.tsx`).
- **What Copy puts on the clipboard: the formatted message and its plain text, together.** The message on screen is the
  message pasted: one preview, editable in place, never a separate page or file to open. Copy writes two versions in one
  step, and the place it is pasted picks: the formatted one (headings, bold, numbered questions, lists, a table where the
  content is a table, named links) for mail and documents, and plain text (numbered lines, "- " lists, "Label: address"
  links) for chat and plain editors. The person never chooses a format; the row's menu has **Copy as plain text** for a
  place that pastes formatting badly. The formatted version is built by the app from the records and the message's own
  structure, every piece of text escaped, with simple inline styles that read well in light and dark mail apps and no app
  colors; the assistant's words are never pasted as markup. Where the browser can't put formatting on the clipboard,
  plain text goes and the toast says "Copied as plain text". The same Copy serves every message: questions to someone,
  a follow-up, the Monday briefing forwarded to someone, a project update, a report to the maintainers. A file to attach
  (a document, a slide deck, a spreadsheet) is the publisher's (6.12; phase C4), not Copy's.
  **Built (B-6b):** one helper, `web/src/lib/copy.ts`, is the only place the app writes to the clipboard (questions, follow-ups,
  nudges, the feedback and keys' text, the ask box); `copyMessage` puts the formatted and plain versions in one clipboard item,
  `copyPlain` the plain text alone (the menu's **Copy as plain text**, toast "Copied as plain text"), and a refused copy
  selects the text for a copy by hand. The formatted version is made from the text on screen, escapes every piece of it, and
  writes only paragraphs, line breaks and links to web addresses. `web/src/lib/copy.test.ts` (the escaping, one test per
  hostile piece), `web/src/components/FollowUps.test.tsx`; the browser test that pastes both into a document and a chat box
  is `web/e2e/acceptance.spec.ts` (3d), written and not yet run.
- **Follow-ups by person or by project** (B-6b): a switch beside the filter. **By project** lists every open question and
  to-do under its project (the ones with none last as "No project"), the person's own first, each row saying who it is with and
  where it stands ("Robin Sample · waiting 5 days · follow up"); its **Open** goes to that person's group, where Copy, Mark sent
  and Record reply are. The switch is not on Today's narrow column. `web/src/components/FollowUps.test.tsx`.
- **Hand an action to the assistant** (B-6b; 6.7 "Handing an action over"): **Hand to the assistant…** is in the menu of the
  person's own to-do (To-dos and questions, Follow-ups' "You" group) beside Mark done and Reassign. It asks what is
  wanted (optional), then queues one `action-work` request, which waits for the person's go above the configured amount like
  any run; the answer is filed as a pending draft of the action's `work` text, reviewed in the text review. The row says the
  assistant has it, waits for the go, or has a draft; the action stays the person's. `tests/test_action_work.py`,

## 7.6 Interaction rules

- Compact rows; details by expanding the row. Tooltips only repeat what is already reachable another way.
- **Toasts never cover a control** (the original designer's mockup review, 2026-10-14; the UI designer's answer 33, 2026-10-19).
  A toast that entirely hid the control with the cursor would fail WCAG 2.2 SC 2.4.11 (Focus Not Obscured), so the fix is
  where they sit, not moving them as the cursor moves. From 1280px they sit at the bottom left of the content area, just
  right of the navigation and never over it; narrower, at the bottom center above the bottom bar. Each is 360 to 420px wide, so
  a toast is one line. The page keeps room under its last row for the stack's height and sets its scroll padding to the same,
  so a row reached by Tab or `j` scrolls clear of the toasts. The same message pushed again is one toast with a count ("Filed 3
  reviews · Undo last", whose Undo takes back the newest); at most three show. A toast goes after `ui.toast_seconds` (0 keeps it
  until dismissed) and waits while the pointer or the cursor is on it; reduced motion means no animation, never longer
  messages. `u` undoes the newest, F6 moves the cursor to the toasts and Esc puts one away and gives the cursor back.
  **Built:** `web/src/lib/toasts.test.tsx` (merging, Undo last, the timer with reduced motion, hold, F6 and Esc),
  `web/e2e/shell.spec.ts` (the corner and width, and Tab through every control with three toasts showing, at 390 and 1440px).
- **One primary action per row; a second answer stays a visible button, a postponement goes in the menu** (the UI
  designer's answers 28 and 31, 2026-10-16). "Keep it open" is the other answer to a held line's question, so it is a
  button beside the primary; "Not now" answers nothing, it only moves the line, so it is in the "..." menu with what it
  does under it ("Back on Today on Thu, Oct 22") and a toast that says so, with Undo ("Off Today until Thu, Oct 22"). A held
  line may therefore show two buttons; every other row shows one (the questions after a move show two as well: Move it to
  Oct 22 and Keep Oct 20, It holds and Needs a change…, 7.7). Every "later" on Today follows the same pattern, so the
  person learns it once. **Built:** `web/src/shell/HeldLines.test.tsx` (the rules review: one button, Not now in the menu
  with its consequence, the toast and its Undo), `tests/test_rule_review.py::test_undoing_not_now_brings_the_line_back_at_once_and_it_says_when_it_would_return`.
- **A held line is the action as a question** (the UI designer's answer 28, 2026-10-16). Its title is the question with the
  item named in quotes ("Close 'Send two spine options'?", "Give 'Book a photographer' to Sam Rivera?", "Drop 'Agree the trim
  size with the printer'?"), its meta line is **one line**: the words it rests on and who said them, nothing else. The reason
  it waits and, for a drop of something that reached someone, who was told and when (in bold) are not on the line: they
  lead the inspector, on the change's card, which has the same two buttons in the same words (B-8, R2). An ending read from
  an input is asked the same way, not as "Keep: Ana finished it" with a Keep button: "Close 'Send two spine options'?",
  "Drop '…'?", "Move '…' to Oct 22?" and "Mark part of '…' as delivered?". Both answers are visible buttons that name the
  result, never "Do it", "Keep" and "Leave it": **Close it** and **Keep it open**; **Change it to Nov 5** and **Keep Oct 30**;
  **Give it to Sam** and **Keep Maya**; **Send it to Ines** and **Keep it with Maya**; **Drop it** and **Keep it**; **Move it**
  and **Keep Oct 20**; **Mark it part delivered** and **Keep it open**. The words that only said "closed" stay the one
  question with three answers ("Done by Ana, or no longer needed?"). After either one a toast says
  what happened, with Undo. The first answer applies the held item (`POST /api/changesets/{id}/ops/{index}/release`); the
  other leaves it as it was (`POST .../decline`, one `held_declined` signal the assistant learns from; Undo is `.../undecline`
  and nets the signal out). The engine shapes the question for the holds that rest on an inference (a close, a date or owner
  change, a routing) and for a drop that reached someone (`engine/held_ask.py`, `QueueLineView.held`); any other held item
  keeps its label and one "Decide" button. *Not built:* "Drop it and draft the note" (the drafted note to the people who were
  told waits for the publisher, 6.12, so the button says "Drop it" and the bold line says who was told), and a note box on
  "Keep it open". **Built:** `tests/test_held_ask.py` (including the change's card carrying the same question and today's
  reason, and a move saying the day it has now), `web/src/components/TodayRecords.test.tsx` (every ask, the line's meta, no id,
  and "Outside" in the pill column), `web/src/components/TodayPromises.test.tsx` (the endings read from an input) and
  `web/src/components/WhatChanged.test.tsx` (the card's two buttons, with who was told leading).
- **One decision is one Today line, and its details hold only that decision** (the UI/UX re-review at `0f37be4`, S1 and S2,
  check C57: no item is on two Today lines). A held op is asked once, under Decide. It leaves the review line of its change,
  which counts only what the assistant did and says how many wait ("1 waits for you, under Decide"; the line's menu goes
  to them); a change whose only ops are held has no review line. Only a held op that has a line under Decide leaves the
  count: one asked of someone else stays in it. Looks good on a change never settles a held op: it marks the change
  reviewed and closes its request, and the held op stays held and stays on its own line (`tests/test_one_decision_one_line.py`).
  A held line opens on the decision alone, never the change it came from: the question, the words it rests on and who said
  them, who was told (for a drop), where it came from (the item's title, with Show source), why it waits (the stored reason,
  in the words of today's checks) and the same answers as the line (`web/src/components/HeldDetail.tsx`); a hold the engine
  doesn't shape as a question opens as its own row and nothing else. Before it is decided, an op's label says what it
  would do ("Would close a to-do", "Would drop a to-do", `op.would.*` in the wording sheet, one for every `op.*`), wherever

- **A line's meta is one line** (the UI/UX re-review of B-7, R3, check C56). On Today every line's meta is cut with an
  ellipsis to one line (Row `oneLine`; the whole text is in the line's inspector and in the page's text), and what came
  from outside is the "Outside" tag in the pill column under the pill, never a word at the end of the meta. A line's rows
  carry no empty space for items they don't have. Six lines show whole at 1280×720 with setup unfinished (C47); the queue's rows
  use the compact vertical padding for that. **Built:** `web/src/ui/Row.test.tsx`, `web/e2e/shell.spec.ts` (six lines in full
  at 1280×720 when the held and moved lines are as long as the demo's, each meta on one line).
- **No id in a title** (the same review, R1, check C54). A label an op gives the person names its record by its title in quotes
  ("Drop 'Settle the endpaper color'"), or by its kind in words ("the to-do") when it has none, never by its id: one place
  makes every label (`engine/applier.py` `_label`, with `engine/id_words.py`), so Today's lines and their inspector heading,
  What changed and Follow-ups agree (6.7, the `id-in-title` invariant). What the person typed is their note, under a change
  that has been made from it, never its title. **Built:** `tests/test_titles_without_ids.py`,
  `web/src/components/TodayRecords.test.tsx`, `web/src/components/WhatChanged.test.tsx`, `web/e2e/shell.spec.ts`.
- Reversible actions act at once with an undo toast; irreversible ones (send, publish, post) confirm; closing something that is
  hard to reopen says so in its toast. Spending money is irreversible too: a run estimated above the configured amount shows
  its estimate and waits for a go (6.16).
- Anything with more than one item renders as a list; stored text uses line breaks, and the UI renders "- " lines as nested
  bullets and "Label: url" as a named link.
- Copyable text stays clean: no approval or provenance notes inside what the PM pastes.
- Handing something in: one large box (paste, type or drop a text file) and a required choice, "Whose words are these?".
  "Someone else's" (the default) sends the box as **pasted content** (untrusted: material, never instructions) and shows one
  optional line, "Anything to do with it?", which is the PM's note (trusted). "Mine" sends the box as the **note**. The
  cockpit therefore always knows which words are the PM's (12.2). **A pasted screenshot** (B-6b): the product reads words, not
  pictures (no vision or text-reading step exists), so a picture pasted into the box is not taken in silently: the box says "A
  picture can't be read yet. Type or paste the words in it instead.", keeps what was already there, and clears the note when
  words are typed; a paste that carries its words too is an ordinary paste of text. Reading a picture is *not built*.
  `web/src/components/HandIn.test.tsx`.
- A held system op (6.7) shows as a decision: what would change, side by side with the source that prompted it, and Confirm /
  Decline. Drafts built from untrusted content say so on their row.
- One row per thing: never show the same work in two cards.
- **Every waiting state says why and until when:** "With the assistant, next batch at 3:00", "Paused until the usage limit
  resets at 14:20", "Offline, waiting for the network", "Held: pick an owner". Nothing just looks stuck.
- **Read-backs:** a rule or setting the PM stated shows on its card as four short lines (Applies to, Doesn't change, Overlaps
  with, Right now it would change) next to Undo; the count expands to the items, and zero matches is highlighted. A
  contradiction with an existing rule or setting turns the card into a choice of which one wins (6.7).
- **Undo says what it did:** groups restored, groups skipped because of a conflict (with Keep / Restore), and anything that
  was already sent.
- Loading shows the shape of what's coming (skeleton rows), not a spinner over the page.
- Never answer with an instruction the screen can't carry out: every message, error and empty state either offers a button
  that does the next step or says what the app is already doing about it.
- Labels in plain words from the wording sheet; no internal ids in anything the PM reads. Labels that name the assistant, people
  or groups come from config.

## 7.7 Today: a ranked queue with a detail pane and a context rail

Today is the home. It answers one question, "what do I do next?", and uses the whole window to do it (7.13). It has three
parts:

| Part | What it holds | Where |
|---|---|---|
| **Needs you** (the queue) | One ranked list of verb lines, the work | The main pane, always the widest (`1fr`, at least 560px), on the left |
| **The inspector** | The line that has the cursor, in full: the assistant's work with evidence, the highlighted source, the message to copy, the decision form, the send-back note | A pane beside the queue from 1680px; below that, the line expands in place |
| **The rail** | Top priorities, This week, Agenda, Your to-dos, Came in, and plugin Today panels | A column on the right (`--rail-w`); below the queue under 1024px |

This supersedes the earlier "a queue, not a dashboard" single column and the 2026-10-11 four-column board (decisions,
2026-10-11 "Today is a ranked queue with a detail pane and a context rail"): the queue is the work and gets the most width;
the informational panels the owner wanted on screen stay visible in the rail, sized to their content, so nothing hides below
the fold and nothing competes with the queue.

**The inspector follows the cursor** (the UI designer's answer 34, 2026-10-19). From 1680px it shows the line that has keyboard
focus, or the one last clicked, from the moment Today opens (the first line, since the keyboard starts there), so focus and
details never disagree. Its title is the line's subject, with "1 of 9 · j / k" beside it on one line (never wrapped; `web/src/components/SmallPoints.test.tsx`). Showing a line is not acting: it never
marks anything seen, read or done. After a line is settled, the cursor and the pane move to the next line, not back to the
top. The line is remembered by its key across live refreshes and for the rest of the session; if it is gone, the pane takes the
line now in its position. With nothing to do the pane says "Nothing needs you" and when the sources are next read; it is never
blank. Below 1680px nothing changes: Enter expands the line in place. **Built:** `web/src/components/Today.test.tsx`.

**Coverage** (6.32, "Coverage on Today"). The heading's second line says what was read and when ("Checked 3 connections, last at
7:40 AM") and names each source that couldn't be read, with since when ("Work mail couldn't be read since yesterday 6:00 PM")
and each not read yet. "Couldn't read" and "read, nothing new" are different words in different styles (the first strong and in
the problem color), so color is never the only sign. The empty queue says "Nothing needs you · Checked 3 connections, last at 7:40

## 7.10 Accessibility

WCAG 2.2 AA as the bar, checked in tests (7.11):

- Every action reachable by keyboard, with a visible focus ring; shortcuts for the review loop: `j`/`k` move, `Enter` expands,
  `a` looks good or approve, `s` send back, `u` undo, `c` copy, `e` edit, `m` then a stage moves a stage item (7.13), `/` Ask, `?` lists the shortcuts. Shortcuts are
  configurable and never fire while typing.
- Contrast meets AA in light and dark themes, including the branding colors from config (the Settings panel warns when a
  brand color would fail).
- Status never by color alone: pills carry words, diffs carry marks and labels.
- Updates that arrive in the background (a job finished, new items) are announced politely to screen readers.
- Reduced-motion preferences are respected; toasts stay until dismissed for anyone who needs more time.
- Changing view moves focus to the new view's heading; closing a drawer or dialog returns focus to what opened it.
- Form controls have boundaries of at least 3:1, and the focus ring is a double ring (a gap in the surface color, then the
  accent) that shows on primary buttons too.
- A heading that takes focus when a screen opens or changes shows no ring: it is not something to press.
- A focus ring never covers text. A row shows its ring for keyboard focus only (not after a click, or when the screen moves
  focus), drawn inside the row's padding, or outside a row that has none.
- Touch targets are at least 44px on a coarse pointer. On any pointer no control is smaller than 24 by 24px (WCAG 2.5.8):
  an icon-only button is at least 32px square (`--target-icon`), a text button at least 24px tall (`--target-min`), and a
  checkbox or radio is itself 24px each way, with its 18px box drawn inside it (`--check-inset`), so the element a person points at
is the hit area; the browser check (C52, `web/e2e/a11y.spec.ts`) measures the element, not its label (R9; `web/src/theme/targets.test.ts`).
  A link running in a sentence is exempt, as the standard says. **Built so far (re-review 3.8):**
  `web/src/theme/targets.test.ts` (the sizes in the styles); the check that no visible interactive element on any main
  screen is under 24×24 is written in `web/e2e/a11y.spec.ts` ("target sizes"), not run.

## 7.11 Front-end architecture

- **React + TypeScript, built with Vite.** The build uses relative asset paths; the router's base path and the API address come
  from the runtime config document (11.2), so one build serves any base path.
- **Server state with TanStack Query**; no global state library. **Live updates over server-sent events** fed by the engine's
  event bus (3.4): an event invalidates the queries it affects, so lists refresh without polling.
- **Types and the API client are generated** from the FastAPI OpenAPI schema (`openapi-typescript`), so Pydantic models stay
  the single source of truth and a changed field fails the web build.
- **Accessible headless components** (React Aria Components) for menus, dialogs, listboxes and toasts; styling with CSS
  modules and **CSS variables** as theme tokens filled from `config/ui.yaml`.
- **Routing:** every view has a real link in the address's fragment (`#today`, `#work/changed`, `#records/people`,
  `#records/person/<id>`), so the one build works at any base path with no server routes, and views can be bookmarked and
  opened in a new tab. **Long lists** virtualized (TanStack Virtual) in version 1.
- **The wording sheet** is a string table loaded at start, with config overrides; components never hard-code user-facing text.
- **Rendering untrusted content:** never raw HTML; Markdown rendered through a sanitizer with an allowlist; external links get
  `rel="noopener noreferrer"`; a link whose label came from untrusted content shows its real domain beside the label, so an
  email can't disguise where a link goes; a strict content security policy with no inline scripts (12.5).
- **Tests:** Vitest with Testing Library for components; Playwright end-to-end runs of the milestone 2 acceptance scenario at
  the root path and under a nested base path, with axe accessibility checks in the same runs. Besides these:
  - the style guide (`#styleguide`, demo and development only) renders every shared component in every state, and is
    screenshot and checked with axe in light and dark at 390, 1024, 1440 and 1920 wide, as is Today;
  - **screen-space checks**: at 1440×900 and 1920×1080 every view's content covers at least 90% of the width beside the
    sidebar with no margin over 48px outside its panes; chrome above the content is at most 56px; Today's first queue line is
    within 140px of the top at 1280×720; at 1920 Today shows the inspector;
  - **stylelint** runs in the web build: no raw color outside the token file; font sizes, spacing and radii only from tokens;
    no `text-transform: uppercase`; no `opacity` on disabled controls.

## 7.12 Visual system

**Character: a calm, dense workbench.** Neutral grays carry structure; **one accent color** marks "act here"; three status
colors appear only where a state changes what the PM should do. Hierarchy comes from type weight, spacing and alignment, not
from boxes, capitals or color. The assistant's work looks like evidence, not chat. Two tests: a screenshot in grayscale still
shows what to do first, and squinting shows two or three weights of mass, not a screen of bordered boxes.

**Tokens.** Every value lives in `web/src/theme/tokens.css`, in three layers: primitives (raw values), semantic roles (what a
value is for) and component tokens (where it is used). Components read only roles and component tokens. Every text pair
meets WCAG 2.2 AA in light and dark; control borders (`--border-strong`) are at least 3:1 against their surface.

**Color roles.**

| Role | Use | Never |
|---|---|---|
| Canvas | The page behind panes | Inside a card |
| Surface | Panes, the queue, header, sidebar, inputs | — |
| Sunken | Quoted sources, code, expanded detail, group headers | Whole sections |
| Accent | The one primary action per row or region; the selected nav item (as a soft fill); links | Decoration, headings, icons that do nothing |
| Accent soft | Selected row, "Needs you" and "Send" pills, the current nav item | Large areas |
| Warn | Waiting for you, held, backup needed, approaching due | Informational notices |
| Danger | At risk, overdue, errors, destructive confirm | Removed text alone (it also gets a mark) |
| Ok | Done, healthy, test passed, setup progress | "Active" on every person |
| Mark | The evidence highlight in a source, search hits | Anything else |

Status always comes with a word; color reinforces it. At most three colored pills in one region of the screen.

**Branding from config.** `ui.brand.color` sets the brand primitive; the app derives the hover, soft and dark-mode shades,
and switches the text on the accent to near-black when white would fall below 4.5:1. `ui.brand.logo` replaces the monogram.
Settings → Appearance shows the measured contrast and warns when a brand color fails (7.10).

**Theme and density.** `ui.theme` (system, light or dark) and `ui.density` (comfortable or compact) are the workspace
defaults; the user menu changes them for this device. Dark mode has no pure black: surfaces are lighter than the canvas,
accents lighter and less saturated, soft fills deep tints. Comfortable is 56px rows and 36px buttons; compact 44px and 30px.
On a coarse pointer, touch targets are at least 44px whatever the density.

**Type.** One family, the system UI font (a brand may set a display face for page titles only). Six sizes and three weights
(`--weight-regular`, `-medium`, `-semibold`: no style sheet sets any other weight, number or word, and the elements a browser
makes bold by itself take the semibold token; the build's stylelint rule `cockpit/weight-tokens` refuses the rest, and
`web/src/theme/stylelint-rules.test.ts` checks it and every style sheet in `web/src`):

| Size | Use |
|---|---|
| 28/34 | Reserved: the empty Today greeting |
| 22/28, 600 | The page title, one per view |
| 18/24, 600 | Pane, section and dialog titles |
| 15/22, 400 or 600 | Body, row titles (600), form values |
| 14/20, 400–600 | Row meta, buttons, labels, nav |
| 12/16, 500–600 | Pills, group headers, captions, timestamps |

Sentence case everywhere; no uppercase label longer than one word. Tabular numbers for times, dates, counts and money.
Paragraphs, messages, pasted sources and the assistant's text are at most 72ch wide **inside their pane**; that limits the
text, not the layout. Labels sit above fields; hints go below. Titles truncate at two lines; names never truncate.

**Spacing and shape.** A 4-point spacing scale; three radii (4px for pills, 8px for controls and menus, 12px for panes and
dialogs); shadows only on things that float (menus, popovers, dialogs, drawers, toasts).

**Shared components**, one each, each with its own styles that read only tokens:
- **Button:** primary (the accent; one per row or region), secondary (a bordered surface), ghost (toolbars and icon
  buttons) and danger (irreversible confirms only). Disabled is a sunken fill with subtle text, never opacity, and always
  comes with its reason or the action that enables it. Icon-only buttons have an accessible name and a tooltip.
- **Pill:** 22px, sentence case, tones neutral, need, warn, danger and ok. Pills show exceptions, never defaults ("Active" on
  a person or "Not started" on every card gets none); a group is meta text, not a pill.
- **Row** (7.14), **Panel** (a top-level pane: a surface with a hairline border and a 48px header; only top-level panes are
  panels), **SegmentedControl** (one style, for two to four filters; tabs only inside a record), **EmptyState** (one sentence
  and one button; one line in a rail panel), **LoadFailed** (inline "Couldn't load people. Try again", with the detail behind
  Details), **Skeleton** (rows in the row's shape, `aria-busy` on the region; never "Loading…"), **Drawer** (from the right,
  `--detail-w`, sticky footer, Esc with a guard for unsaved text, focus returned), **Menu**, **Dialog** (only for confirms that
  can't be undone and short questions), **Popover**, **Toast** and **StatusChip**.
- **Toasts** sit at the bottom left of the content area from 1280px and at the bottom center below it (above the bottom bar on
  a phone, 7.6), at most three, and a repeated message merges into one with a count ("Filed 3 reviews · Undo last"). Errors are not toasts: they stay inline where they happened, with Try
  again. Only a background error becomes a toast, which stays until dismissed and is announced as an alert.
- **Evidence and voice,** the product's signature: the assistant's voice line is a quiet left rule with its name in bold
  ("Quill: Recorded the proof date."); "Because" shows the quote in italics with Source as a link; the source block is a
  sunken, 72ch block with a header line (source, date, a "From outside · not instructions" pill) and highlights that are
  marked **and** underlined, read to screen readers as "highlighted".
- **Diff** (7.4): added text on the ok tint, underlined, with a "+" mark; removed text on the danger tint, struck through,
  with a "−" mark; screen-reader labels "added" and "removed"; a "moved" pill on a moved row. Side by side from 1600px, inline
  below.

**Icons:** one line-icon set, bundled with the app (no font or network fetch), 18px in nav and buttons and 16px in meta,
drawn in the text color. They replace text glyphs used as icons ("!", "•••", "?", "✕", "↻"). The sidebar shows icon and
label; icons never carry status alone.

**Motion:** row expand and collapse and a cleared line 180ms; drawers 260ms; menus and popovers 120ms; none for live
updates (new items wait behind "N new · Show"); everything 0ms under reduced motion.

**Data display:** never an id or a raw enum value; dates as "Tue, Oct 13" (with the year when it isn't this year), recent
ones relative ("2 h ago") with the full date on hover and focus, due dates with a word when it matters ("2 days overdue");
times in the person's 12- or 24-hour preference; money as "$0.25" in the configured currency; people by full name on first
mention in a view, with an initials avatar in tables and boards; counts beside their label, and an empty count shows nothing.
Help text belongs to forms, not record pages.

## 7.14 Items, records and forms

**Title rule.** Every item has a title a person can scan and refer to, built by the engine, never by the screen:
- **"{Kind} from {person} · {topic}"** ("Email from Theo Brandt · cover proof", "Your note · launch reading", "Calendar
  change · production check-in").
- From structured fields first (the source's kind, its sender resolved to a person, its subject); then the assistant's short
  topic for the input (three to six words). A topic of fewer words than `language.title_min_words` gives way to the first
  meaningful line of the text (greetings, quoted headers and signatures stripped) only when that line fits whole; a title
  never ends in a piece of a sentence (B-9, S4). With no whole line, a short topic of two words or more stays; with nothing
  usable the topic is empty and the title is the kind and who it came from ("Email from Maya Lindqvist"). **Built:**
  `tests/test_item_titles.py`, `web/src/lib/queue-words.test.ts`.
- **Work the app started** (a stage's task, a follow-on after a move) is titled by its kind of task and what it is about,
  not "Work Quill started": "Filing notes · Cover review" (`Title.task` and `Title.subject`; a kind of
  task the wording sheet doesn't name reads as the assistant's work). A kind with a `queue.title.task_what.<kind>` entry is
  titled by what happened to its subject, never by the name of the run: a follow-on after a move reads "After 'Cover
  review' moved". **Built:** `tests/test_item_titles.py`,
  `web/src/lib/queue-words.test.ts`.
- What changed uses the same title as Today for the same item, never the first line of what came in ("From: Jun Park"): the one
  words function, `titleWords` in `web/src/lib/queue-words.ts` (R10; `web/src/components/WhatChanged.test.tsx`).
- A title never starts with a greeting, "From:" or a cut-off sentence, and never ends in one.
- What the assistant did is said as the **outcome**, not a count of things: "Filed 1 note", "Added 3 actions · 1 waits for
  you", "Recorded the proof date".

**Row anatomy.** Every list row has the same parts at the same x on every row of every list:

```
[Pill]   Title (15/600, at most 2 lines)                       [Primary]  [•••]
128px    Meta: source · person · date · project (14/400 muted)
```

  right-aligned; the menu is always the last thing on the row. Every line of Today uses the same columns, the lines that

  Focus: the double ring. Hover: the hover surface.
- Expanded content indents to the title column on the surface, with its items divided by dashed hairlines.
- **At most two levels:** a line, then its items. Evidence and the source sit inside an item as a sunken block, never another
  bordered card. Nowhere has more than two levels of bordered containers.

## 7.15 Connections, accounts and add-ons

**Connections** is a sidebar entry (7.1), not a Settings section; it was called Sources until the UI re-review of 2026-10-21 (decisions, "The area for what the assistant reads is called Connections"), and a source in the configuration is still a source. Above the connections it holds **Accounts**: the services an
add-on signs in to (mail, calendar), one row each (decisions, 2026-10-12 "Signing in is the whole setup for mail and
calendar").

- **An account row** says where the sign-in stands in words, with one primary action: Sign in, Sign in again, or, once
  signed in, the next step. Signing in leaves the app for the service's own page in this tab and returns afterwards.
- **Signing in starts reading.** The sources the add-on declares (the inbox, the main calendar) begin as soon as the person
  signs in, once, and only where nothing reads with that connector yet. Nothing has to be chosen first. The first read of a
  source a sign-in starts also hands the assistant the last day's items (a setting), so the person sees a result and not an
  empty list.
- **What isn't read yet.** A signed-in account whose sources were removed or never started shows "Not read yet: ..." with
  **Start reading**, which brings them back. Choosing other sources, narrowing or removing them comes after, and the
  person's changes and removals stand.
- **Using an app registration of one's own.** The add-on's registration is the default, so the person only signs in. A person
  who wants their own pastes it on the account row beside numbered steps the add-on supplies; it can be set aside and brought
  back (decisions, 2026-10-11 "Signing in needs no app registration from the person").
- **A source's menu** has **Read now** (read it again at once), **Look at the last day** (hand the assistant what arrived or
  happens near now, or a folder's files modified in the last day, for a source whose first read only noted what was there; the
  add-source form's first-read hint points to it), Change, Turn off or on, and Remove. Failures
  say what to do on screen and never point to a settings file (10.5).

**Add-ons** has Installed and Available (3.11). Turning one on or off acts at once with Undo.
- **Install** (decisions, 2026-10-11 "One-click install for add-ons comes before the freeze"). An Available pack gets an
  Install button. The app downloads the release the catalog names, checks its checksum, installs it beside itself and
  offers Turn on. Update and Remove work the same way. Built (phase A2) for releases of pure Python; the introduction says
  installing happens here after the person has looked. A pack with no release still shows its install command to copy.
- **Turning on.** A pack turned on that needs a restart shows "On after a restart" until the person chooses Restart now (the
  restart rule). Installing a pack leaves every other add-on as it was; an add-on starts off until the person turns it on.
- **Before install** the screen shows what will be added and refuses what conflicts with the app's own libraries; Remove
  takes out only what that pack needed (roadmap phase A2, see roadmap-done.md; planned). A private pack's release host takes a read token the
  person gives once, kept as a secret reference (12.1).

instead of waiting for their schedule, and says what it found: "2 new items", "Nothing new", and "Couldn't read 1 connection. See Connections" for any source that failed (owner request, 2026-10-12; built, phase A2). The button shows while a

## 7.16 AI accounts take over the work

A real AI account does the assistant's work as soon as it is added.

  real account stay where they are. If the person chose what the account is for, that choice stands.
- An account that does no work yet offers **Use for the assistant's work** in its menu: everyday work goes to its first
  model and harder work to its harder one, with an undo toast ("Quill now works with <account>").

  each kind of work with that work's exact settings (6.16), and only when every check passes is it added to those kinds'

- **The Learned line.** A correction's card (a send-back, an undo, a dropped question, an edited follow-up) gets one line
  under it: "Learned: <the lesson, rule, term, routing or style note in plain words> · Keep · Just this time · Edit ·
  Discard". Keep makes it active; Edit opens it in a drawer; Discard marks it discarded, with an optional reason (5.1).
  **Just this time** (the original designer's mockup review, 2026-10-14): the correction was right but is not a pattern
  (the usual owner was out); it records the signal, makes no proposal, and counts toward a later proposal if the same
  correction repeats. Discard says the assistant got the lesson wrong, which is a different thing. **The lesson is about
  what was corrected:** an action's owner changed teaches who does that work ("catering work goes to Ines"), not where
  questions go; a lesson that generalizes further says both. Learning from the person's own words is already kept and shows Undo
  instead. "Overlaps with …" links an entry it would merge with. **Built so far:** a proposal that says what another active
  or proposed entry says over an overlapping target (the duplicate rule of 6.22, `proposals.duplicate_of`, asked for the
  proposal itself) carries `overlaps_with`, and its line adds "Overlaps with: <that entry> · kept" (or "· waiting"), linked to
  the entry's page for a rule or fact and to the Knowledge screen otherwise. A proposal that merges on arrival never reaches
  the line; this shows the cases that stand beside another entry (a meaning proposed beside a term the person kept as
  unknown, a reach widened with Keep for, an entry kept or edited since). Built: `tests/test_learned_lines.py` (the
  "Overlaps with" tests), `web/src/components/Learned.test.tsx` (the overlap tests). Only the Learned line shows it; the
  Review list on Today and the Knowledge screen don't yet.
- **What the server gives these screens** (built in L3p): `GET /api/knowledge/proposals` (the proposals, with `came_from`,
  evidence, target, `just_this_time_before` and `expires_at`), `GET /api/knowledge/catch-up`, `POST /api/knowledge/{id}/just-this-time`,
  and the Today lines `learned` and `catch_up` (6.22). The screens themselves are phase B's.
- **Keep shows exactly what will be kept:** the assistant's restatement and its target, with the source beside it as
  evidence marked "from outside" when it came from content. **Keep all** on the daily card covers only glossary terms and
  facts with evidence. Routing, rules and lessons are kept one at a time (12.8).
- **Keep for: this project ▾.** The reach is on the line, not inside Edit, and defaults to the narrowest target the
  correction supports: this item's kind of work on this project. Widening it is one click; undoing an over-broad lesson
  after it has misfired is much more work. Over-application was the running version's worst learning failure.
- **When it appears.** When the person wrote a note (a send-back, an answer to the assistant, a rule stated in Ask), the line
  appears on that card within seconds, while they are still looking at it. Learning from silent corrections shows on their
  cards after the next batch.
- **On Today: one line for everything learned** (merged after the original designer's mockup review, 2026-10-14).
  Proposals from inputs and from silent corrections (an undo, an edited follow-up, which arrive on a card the person has
  already left) are one Review line: "Review 7 things the assistant learned", each entry tagged by where it came from (an
  input, or one of your corrections), saying how many from inputs expired unreviewed since the last one. Proposals from
  silent corrections never expire. Proposals from corrections made while the person was there stay on their own cards, as
  the inline Learned line.
- **Which knowledge shaped this.** The assistant's work shows the knowledge it applied (`applied`, 6.20) on its evidence
  line: "Because you told me: questions about release dates go to the schedule, not to people", linked to the entry. The
  person sees the assistant learning day to day, which the rates on Quality never show. When a wrong output came from a
  wrong lesson, the entry's menu has **This doesn't apply here**: narrow its target or retire it, right there, instead of
  correcting the output again and again. That is the fastest cure for over-application.
- **Use on every knowledge row.** On the Knowledge screen and a project's "what the assistant knows", each entry shows its
  use from the knowledge log: "Used 12 times · last 2 days ago", or "Never used". That is how a person judges whether to
  keep, narrow or retire it, and it explains the unused list. **Built** on the Knowledge screen: `used` (runs whose log
  applied the entry: a rule the log counts as applied, or an entry the run's changeset cites among those it was given),

## 7.19 Notifications: "needs you", and only that

*Built in part* (phase B-6b; from the first design author's review). Opt-in, off by default. A notification is
sent only for what Today's Decide group holds, so the notification and the screen never disagree:
- a decision is waiting;
- a draft the person would want to review is ready;
- something is broken and needs them: work stopped, waiting for a restart, or a backup failing.

Never for routine processing. One line, leading with the action ("Answer: who owns the cover brief?"). Quiet hours are
respected (`ui.notifications.quiet_hours`).

**Where they go.** A notification target is a channel like any other (6.3), configured once and checked with **Send me a
test**. The phone doesn't need to reach the app; the app reaches something the phone already receives, anywhere, from day
one:
- **the browser's own notifications** on the computer running the app;
- **mail to the person themselves;**
- **a webhook,** which covers a chat app's incoming messages and push-notification service topics.

A webhook's address is a secret reference, like a key (12.1).

**Two guards:**
- **To the person only.** A notification target sends only to the person's own address or webhook, never to anyone else.
  So it needs no per-message approval: the person approved the target and its test. It is the one outward channel that
  works this way.
- **Little content by default.** A push service or chat app is a third party, so a notification carries the action and a
  count ("2 decisions waiting"). Titles go only to targets the person marks as allowed for that data level, and restricted
  items never.

**Built so far** (phase B-6b; tests: `tests/test_notifications.py`, `web/src/components/Notifications.test.tsx`,
`web/src/components/TodayReminders.test.tsx`; the designer's F18: before mail sending, the browser and a webhook now, mail
to the person themselves listed as coming with mail sending):
- **What is sent, and when.** A notice is for the items in Today's Decide group: the core's own lines and the lines an add-on
  puts there (`engine/notifications.py`, `decide_keys`). When one comes in that the person has not been told about, one notice
  says how many wait now ("2 decisions waiting for you"); the same items are not told again, a restart included (the keys told
  are kept in the workspace's private folder), and an item that is dealt with and comes back is new again. Nothing is sent in
  quiet hours (`ui.notifications.quiet_hours`, on the person's clock); what came up then goes out once when they end. A note
  that could not be delivered is tried again after `ui.notifications.retry_minutes`, and Settings says why in plain words.
- **Where it goes.** *The browser:* the open screen shows the notice as the browser's own notification when something new comes
  into the Decide group, only with the browser's permission, which a button in Settings asks for and never a page load;
  what was waiting when the app opened is not announced (`useNeedsYouNotices`, `GET /api/notifications/waiting`). *A
  webhook:* the person's own address (a chat app's incoming-message address or a push topic), kept as a secret reference like
  a key (`POST /api/notifications/webhook`; typed on a local app and kept in the private keys folder, or named as `env:` or
  `file:`; never in a settings file, the ledger, a log or an answer), posted as a small JSON message or as plain text
  (`webhook_format`). Only that one host is reached, over https (http on this computer only, never in a hosted app). *Mail to the
  person themselves:* listed on screen as coming with mail sending; nothing is built for it.
- **Send me a test** on each target (`POST /api/notifications/test`): the webhook gets the test note now, even with notices
  off, so it can be tried first; the browser shows the test notice itself. Each says how it went.
- **Two guards, as built.** To the person only: the one address is the one the person gave, and a notice has no recipient
  field. A count only: a notice never names what an item is about, so there is nothing for the data level to hold back.
  *Not built:* titles for a target the person marks as allowed for a data level (`detail: titles`, `allowed_data`).
