# Part 7. UI specification (React)

## 7.0 Principles

- **A queue, not a dashboard.** The PM's day is a list of decisions. The home screen is **Today** (7.7): one ranked list, each
  line actionable where it stands. Panels are filtered views of the same items, reached from Today or the tabs.
- **One primary action per row, always in the same place.** Other actions go in the row's "…" menu. The primary action is the
  likeliest next step for that row's state (Looks good, Copy, Answer, Approve, Pick an owner).
- **Undo instead of "are you sure?".** The ledger makes almost everything reversible (6.7), so reversible actions happen at
  once with a toast ("Closed 3 actions · Undo"). Confirmation is only for what can't be undone: sending, publishing, posting.
- **Keyboard first, touch friendly.** Everything is reachable by keyboard (7.10); everything also works on a phone (7.1).
- **Edit in place.** A question, message or draft can be edited where it is shown, then approved; the PM's version is what's
  approved (content hash, 6.12) and the edit is a quality signal (6.20).
- **Show why.** Every claim the assistant made shows its evidence ("because: '...'"), and opening it shows the source with that
  passage highlighted (6.7).
- **Nothing moves under the PM.** New items arriving while the PM reads appear as "3 new · Show" at the top, never by pushing
  rows around.
- **Plain words.** Every label, message and empty state comes from one **wording sheet** (a string table, overridable by
  `config/ui.yaml` and translatable later). Internal terms (changeset, op, tier, held, ledger) never reach the screen; the sheet
  maps them to plain words ("what the assistant did", "waiting for you").

## 7.1 Shell and layout

- One header bar: product name and logo (from `config/ui.yaml`), date, live indicator and last check, tabs, a Today button with
  a count, the **Ask** box (6.25), configurable quick links, Refresh, a Jobs menu, Log, the age of the last backup and a mark
  when there is no off-device backup (4.15).
- **Responsive:** one column below a configurable width (default 900px), with the header collapsing to a menu. On a phone the
  tasks that matter most are first class: review and approve or send back a draft, copy a message, answer a decision, hand
  something in (paste, or share text to the app). Installable on the home screen as a web app is a version 1 item.
- Tabs and their panels come from a **panel registry**: the core registers its panels, plugins register theirs, and
  `config/ui.yaml` may reorder or hide them. Default layout:
  - **Today** (home, 7.7).
  - **Work tab:** Automation problems (when any), What changed (7.3), Waiting to go out (7.4), Follow-ups (7.5), My meetings.
    Two columns on wide screens, one on narrow ones.
  - **Portfolio tab:** project health table grouped by the configured grouping; each project opens to its RAID (risks, issues,
    assumptions, dependencies, decisions) as configured in `config/raid.yaml`; plugins add sections.
  - **Admin tab:** request an update; the assistant's queue; plugins (enabled, version, what each may reach, its automation
    problems); **Settings** (7.9); **Quality** (6.20); **Rules** (6.21); **Security** (who is signed in, recent sign-ins and
    failures, deploy check results when hosted).
  - A tab per pack when the pack declares one.

## 7.2 Plugin panels

Plugins describe panels declaratively, so most need no front-end code and every one looks and behaves like the core:

```yaml
panel: personal-projects/goals
title: Goals
tab: work
source: {record_type: personal-projects/goal, filter: {status: open}}
view: table                                   # list, table, board, form, detail or compare
columns: [title, project, due, status]
primary_action: personal-projects/goal.update # the one action shown on the row
row_actions: [personal-projects/goal.close]   # the rest, in the row's menu; each runs as an op through the applier
```

Besides list, table, board, form and detail, the core offers a **compare** view for versions of a `long_text` field that any
panel can use: two-way (a pending draft or proposal against the current version) and three-way (base, current and handed
back, when the base moved after a working copy went out). It reuses the diff rendering of 7.4 (marks and screen-reader labels,
never color alone), moves change by change from the keyboard, and lets the person accept or reject each passage, or pick a
side in three-way; the choices submit one `text.accept` (6.7). The plugin names the field and the pending version; it writes no
diff or front-end code.

The panel spec is itself a JSON Schema, so a plugin's panels are validated like the rest of its manifest. Row actions and forms
submit ops, so plugin UI can't bypass validation, tiers or the ledger. A bundled plugin that needs more may ship a React
component, registered at build time against the same panel interface. Loading plugin components at runtime waits for a real
need.

## 7.3 What changed (one list for incoming changes and the assistant's work)

- One row per incoming change (source tag, linked title, state pill). The assistant's work for that change is nested inside
  ("What the assistant did (N)"), each item with its evidence line, next to "Show the change" (word-level diff). Details open by
  expanding the row, not in tooltips.
- One row per piece of the assistant's own work that didn't come from a change (requests, answers), tagged with the
  assistant's name. Automation problems are not here; they live on their own cards (6.13).
- **Primary action by state:** new change: Process with the assistant; reviewed: **Looks good** (closes the change and files
  its work); auto-closed: This is ours. In the menu: Done, Ignore, **Send back** (required note; option "Undo it, then send"),
  Undo, Take a closer look.
- **Automation problems** (above What changed when any are open): one card per problem, saying what happened and what the
  cockpit is doing about it; primary action Draft a report, menu Dismiss.
- Filter: Needs attention, Processed, With the assistant, The assistant's own work, Done, Auto-closed, Ignored, All.
  "All looks good" for the reviewed rows shown, with an undo toast.

## 7.4 Waiting to go out

- Every draft for every channel in one list, grouped by channel. "Review changes" runs the dry run.
- Per draft: checkbox, title (left-aligned, wraps beside the checkbox), tags (new, dashboard view, wording check, scheduled,
  "built from outside content"), and a plain-words count ("3 changed, 2 added, 1 removed, 1 moved"). Primary action Approve;
  the draft can be edited in place first.
- Each channel's output type picks its preview. Pages: inline word-level diff by default, side by side as an option (version
  1); removed text is struck through **and** marked, added text underlined **and** marked, with screen-reader labels ("removed",
  "added"), never color alone; a mostly rewritten line shows old then new in full; small unchanged bits between changes fold
  into the change so phrases read old-then-new; table rows show cells joined cleanly with empty cells as "—"; a row that only
  moved shows once with a moved mark; a moved row whose cells changed shows as one in-place change. Short posts and messages:
  the full text as it will appear, with the channel's limits and a character count.
- Sending is the one place that confirms: a send message is required where the channel records one; sending a subset warns if
  a roll-up includes unticked drafts' changes. Success notes fade; errors stay with the offending lines and an "Ask the
  assistant to reword" button.

## 7.5 Follow-ups

- **Filter:** "To send" (default) and "Waiting on them", styled like What changed's filter. Items already sent or told show
  only under Waiting on them.
- **To send, by person:** "You" first (decisions with Answer; your action items), then everyone with something still to send,
  A to Z, one card per person. Only people in the tracked area and domain contacts get a card; a contact's cross-domain
  questions are grouped under the domain's name. Header: the name, "N to send" and **Copy N** (primary), plus **Send** when the
  person has a channel configured in `how_to_reach` (it creates a draft that waits for approval like any other). Opened, the
  card has "In this message" (a plain list of what is still to send, with project and due date, no per-item buttons), then the
  message box and Copy.
- **Copy, then Mark sent** (two steps). Copy shows the message it will copy, editable in place, and puts it on the clipboard
  only; nothing is recorded ("Copied" confirms). After a successful copy the card's primary action and the button under the
  box become **Mark sent**, which records the box's text as sent and shows an Undo toast ("Marked as sent to Ines"); the
  items then move to Waiting on them. The "copied" state lives in the component only. The card's menu always offers Mark sent,
  so it can be done after a reload or after sending some other way. The message has a greeting with first name, questions
  first (numbered when several), then "Action items with you:" as a list with project and due date, then one closing line, for
  items still to send only. No title-then-same-text repetition. If the browser blocks the copy, nothing changes and Copy stays.
- **Waiting on them:** one card per person, one line per item with "sent <date> (N days)" and its own step: They finished it
  for an action, Record reply for a question. In the menu: Reassign (name picker with full names), Take care of this (the
  PM's own). No message box or Copy here.
- **By group:** actions with each project's open questions, copyable per group, per project or all. Notices don't appear as
  questions here.
- Question lines under Waiting on them: Record reply; menu: Respond to the assistant. Decisions: primary Answer.

## 7.6 Interaction rules

- Compact rows; details by expanding the row. Tooltips only repeat what is already reachable another way.
- Reversible actions act at once with an undo toast; irreversible ones (send, publish, post) confirm; closing something that is
  hard to reopen says so in its toast. Spending money is irreversible too: a run estimated above the configured amount shows
  its estimate and waits for a go (6.16).
- Anything with more than one item renders as a list; stored text uses line breaks, and the UI renders "- " lines as nested
  bullets and "Label: url" as a named link.
- Copyable text stays clean: no approval or provenance notes inside what the PM pastes.
- Handing something in: one large box (paste, type or drop a text file) and a required choice, "Whose words are these?".
  "Someone else's" (the default) sends the box as **pasted content** (untrusted: material, never instructions) and shows one
  optional line, "Anything to do with it?", which is the PM's note (trusted). "Mine" sends the box as the **note**. The
  cockpit therefore always knows which words are the PM's (12.2).
- A held system op (6.7) shows as a decision: what would change, side by side with the source that prompted it, and Confirm /
  Decline. Drafts built from untrusted content say so on their row.
- One row per thing: never show the same work in two cards.
- **Every waiting state says why and until when:** "With the assistant, next batch at 3:00", "Paused until the usage limit
  resets at 14:20", "Offline, waiting for the network", "Held: pick an owner". Nothing just looks stuck.
- **Read-backs:** a rule or setting the PM stated shows on its card as four short lines (Applies to, Doesn't change, Overlaps
  with, Right now it would change) next to Undo; the count expands to the items, and zero matches is highlighted. A
  contradiction with an existing rule or setting turns the card into a choice of which one wins (6.7).
- **Undo says what it did:** groups restored, groups skipped because of a conflict (with Keep / Restore), and anything that
  was already sent.
- Loading shows the shape of what's coming (skeleton rows), not a spinner over the page.
- Never answer with an instruction the screen can't carry out: every message, error and empty state either offers a button
  that does the next step or says what the app is already doing about it.
- Labels in plain words from the wording sheet; no internal ids in anything the PM reads. Labels that name the assistant, people
  or groups come from config.

## 7.7 Today (the home screen)

One ranked list of what needs the PM, built by the Today builder (6.15). Each line starts with what to do and shows the one
primary action for it: answer 2 decisions (Answer), review 4 drafts (Approve, after a look), look over 6 changes (Looks good),
send 3 questions to a person (Copy), follow up on 2 waiting 5 days, finish your overdue action, review proposed lessons, pick
an owner. A line expands in place to its items; working through them clears the line. A line for many items links to the
filtered panel. Nothing informational sits on Today: if there's nothing to do, it says so and shows when the next check is.

In the launch slice, the home screen is a single column with What changed and Follow-ups; Today as the queue arrives in
version 1 (13.1).

**Reference prototype:** `prototypes/today.html` (open it in a browser; fictional imprint data). It shows the queue, one
primary action per row, evidence lines with highlighted sources, edit-in-place before copying, held actions, proposed lessons,
undo toasts, the "1 new · Show" pill, the hand-in (the prototype still shows two boxes) and the keyboard shortcuts. Build to its behavior; its styling is a
starting point, replaced by the theme tokens of 7.11.

## 7.8 First run

A new workspace opens to a short setup, each step skippable and repeatable from Settings:

1. Name the workspace and pick a starter preset (a small imprint, a workplace PM, personal projects), which sets packs, RAID
   records and playbooks.
2. Add an AI account and press Test (6.16).
3. Set up an off-device backup (4.15).
4. Add a few people (or paste a list for the assistant to read).
5. Hand in a first note, and see what the assistant did with it.

## 7.9 Settings

Forms are generated from the config schemas (4.0), then made usable: grouped by file and topic; basic keys first, advanced
behind a toggle; search across every key; each key's description, default and "what reads this" (from `config explain`)
inline; validation as you type; keys locked by an environment variable or flag show where they come from. Secrets are entered
once into the keychain and shown only as references. Saving shows a read-back when the change has effects to show (6.7).

## 7.10 Accessibility

WCAG 2.2 AA as the bar, checked in tests (7.11):

- Every action reachable by keyboard, with a visible focus ring; shortcuts for the review loop: `j`/`k` move, `Enter` expands,
  `a` looks good or approve, `s` send back, `u` undo, `c` copy, `e` edit, `/` Ask, `?` lists the shortcuts. Shortcuts are
  configurable and never fire while typing.
- Contrast meets AA in light and dark themes, including the branding colors from config (the Settings panel warns when a
  brand color would fail).
- Status never by color alone: pills carry words, diffs carry marks and labels.
- Updates that arrive in the background (a job finished, new items) are announced politely to screen readers.
- Reduced-motion preferences are respected; toasts stay until dismissed for anyone who needs more time.

## 7.11 Front-end architecture

- **React + TypeScript, built with Vite.** The build uses relative asset paths; the router's base path and the API address come
  from the runtime config document (11.2), so one build serves any base path.
- **Server state with TanStack Query**; no global state library. **Live updates over server-sent events** fed by the engine's
  event bus (3.4): an event invalidates the queries it affects, so lists refresh without polling.
- **Types and the API client are generated** from the FastAPI OpenAPI schema (`openapi-typescript`), so Pydantic models stay
  the single source of truth and a changed field fails the web build.
- **Accessible headless components** (React Aria Components) for menus, dialogs, listboxes and toasts; styling with CSS
  modules and **CSS variables** as theme tokens filled from `config/ui.yaml`.
- **Routing** with React Router; **long lists** virtualized (TanStack Virtual) in version 1.
- **The wording sheet** is a string table loaded at start, with config overrides; components never hard-code user-facing text.
- **Rendering untrusted content:** never raw HTML; Markdown rendered through a sanitizer with an allowlist; external links get
  `rel="noopener noreferrer"`; a link whose label came from untrusted content shows its real domain beside the label, so an
  email can't disguise where a link goes; a strict content security policy with no inline scripts (12.5).
- **Tests:** Vitest with Testing Library for components; Playwright end-to-end runs of the milestone 2 acceptance scenario at
  the root path and under a nested base path, with axe accessibility checks in the same runs.
