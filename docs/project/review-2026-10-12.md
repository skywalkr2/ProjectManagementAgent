## 2. Why small errors keep reaching the owner

Every problem the owner found in the last two days, grouped by its cause. The examples are the actual reports.

### Cause 1: the "try it" path runs on test fixtures

The README tells a person to create their workspace from `workspaces/demo-b`, the fictional imprint whose job is to
exercise every setting for the tests. So the owner's real workspace carried:
- example AI accounts with no keys ("Key not found" on three accounts, raised twice);
- the `/admin` base path (Google refused the sign-in);
- a renamed label ("Chasers");
- a synced folder setup that collided with another workspace.

A fixture's job (cover every shape) and a starter's job (work with nothing set) are opposite, and one folder did both.

### Cause 2: every default was "safe", so the whole produced nothing

Each was chosen to avoid surprises, and each is reasonable alone:
- mail reads nothing until a label is chosen;
- a first read only notes what is there;
- adding an AI account doesn't switch the work to it;
- add-ons start off;
- the agenda shows one day.

Together, a person who signed in to Google and added an AI account got no result at all. No test or review asked
"after setup, does the person see a real result?"

### Cause 3: no test follows the person's journey

All 33 end-to-end tests start from the demo workspace with the stand-in assistant. These paths have no test from start
to finish (audit, Goal 3):
- fresh workspace → AI account → hand-in → Today;
- sign in → mail read → assistant → review;
- a source added on screen → read → assistant;
- installing an add-on;
- backup → restore;
- restart.

Each piece is tested alone, so the joins break, and the owner is the one who finds them.

### Cause 4: fixes went to the symptom, and the rules weren't checked where they apply

- The unused AI accounts were "fixed" once by filtering the test list. The accounts stayed, and the owner raised it
  again.
- The rule "no command, file name or config path on screen" is checked only in the screens' own code. About 50
  messages built by the server still name `ai.yaml`, `watch.yaml`, `env:NAME`, `requires.secrets` and `cockpit …`
  (audit Parts 1–7, flag 3).
- `workspace.owner_format`, `storage.export.every_minutes` and `storage.export.remote` are settings with no effect. The
  config coverage check doesn't catch unused keys.

### Cause 5: too much at once, and validation skipped

There were 149 commits in three days, across these streams at once:
- the UI redesign;
- plugin question rounds 26–37;
- the mail add-on and the catalog;
- the owner's fixes.

The plan for this period is owner validation before the 2026-10-30 go/no-go: run the scenario and a week of real
notes. Instead, version-1 features were built (plugin API from 0.3.30 to 0.3.55, interfaces, synced folder, stages, the
redesign) while the basics hadn't had a steady run. The session's own context was compacted several times, and what was
promised slipped through the gaps (the Install button).

### Cause 6: what lives outside this repository has no checklist

- **The service setup.** The Google Calendar API had to be turned on in the cloud project.
- **The add-on's defaults.** The mail add-on followed an "opt-in" rule that the owner never wanted.
- **The update steps.** A new build tool meant `npm install` before `npm run build`, and `uv sync` needs `--inexact` to
  keep an installed add-on. Each was found by the owner, one at a time.

## 3. What changes now

1. **A starter, separate from the fixtures.**
   - `cockpit init` with no template is the documented start; the README and `docs/install.md` say so.
   - The demos stay for tests and the sandbox (`cockpit demo`).
   - A self-check verifies that a fresh workspace has no account, source or setting that shows a problem.
2. **"Produces a result" as a rule in CLAUDE.md.**
   - Every default must lead to a visible result for a real person with no file editing.
   - Every feature's brief says what the person sees in their first five minutes.
3. **Journey tests.** Playwright, with a fake AI service and fake mail and calendar services:
   - fresh workspace → add an account → hand in → result on Today;
   - sign in → mail and calendar read → assistant → review on Today;
   - add a source on screen → result;
   - install an add-on from the screen → turned on → its screens appear;
   - backup → restore;
   - acceptance scenario steps 1–7 complete, step 6 included.

   Nothing is "ready to test" until these pass.
4. **Server-side wording checks.**
   - A scan of `engine/` and `api/` strings that reach the screen bans `.yaml`, `env:`, `cockpit `, dotted key paths
     and manifest field names.
   - Config coverage fails on keys nothing reads.
   - The roughly 50 strings found are rewritten, or put behind Details.
5. **Fix the cause, then look for its siblings.** A reported problem gets a failing test of the person's path first.
   Then everything with the same cause is searched for and fixed in the same change, and the reply names what was
   checked.
6. **One update command.** `cockpit update` (or a script) runs `git pull`, `uv sync --inexact`, `npm install` and the
   build, so updating never needs a list of commands.
7. **One stream at a time until validation passes.**
   - Plugin question rounds are answered in one batch a week.
   - The redesign continues only after the journey tests exist.
   - "Ready to test" messages carry the exact commands and what the person should see.
8. **External setup checklists.** Each add-on's help lists what must be turned on at the service (APIs, scopes,
   consent screen). Each add-on maps "the service isn't set up" errors to words that say exactly that.

## 4. Recommended order from here

1. **The person's path works** (from the flags in the audit):
   - the Install button on Add-ons;
   - crashed runs re-queued;
   - the test-only "stand-in source" hidden from Add a source;
   - secrets for core mail and calendar entered on screen (kept like an AI key) instead of only `env:` or `file:`;
   - the server-side wording fixes;
   - the starter workspace and one update command;
   - the journey tests;
   - a refresh button on the mailbox (owner, 2026-10-12: Today's "Came in" and the mail source can be checked now
     instead of waiting for the schedule).
2. **Owner validation:** the acceptance scenario run by the owner, a week of real notes and mail, then a go / no-go on
   the date the owner sets. The plan documents are updated to say which dates still hold.
3. **The redesign:** Today as the ranked queue first (the engine is ready), then records and Settings, as planned.
4. **The governor** (re-queue, stale sweeps, scheduled export) and **restore**: they protect real data.
5. **Version 1 musts in scope order:** the publisher and Waiting to go out, scope and facts, dependencies and
   baselines, lessons and glossary.
