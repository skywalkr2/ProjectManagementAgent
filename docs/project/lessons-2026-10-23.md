# Lessons from running, 2026-10-23: versions, endings, a loop that can't die, and lead time

From the owner, as received. Tracked as open promises P51 to P54. Each lesson's rules and tests are the brief; check the
code first and say what it does today.

## 1. A shared folder holds versions of one document, and only the newest one counts

The person keeps a working deck in a shared folder and saves it under a new name at each round ("<deck> FOR REVIEW",
"_v2_0", "_v2_1", "_v3", "_v3_1"), moving the old ones into an Archive subfolder. Every save and every move was filed as
its own change. The assistant read each one and kept comparing the newest deck with facts it had recorded from older
copies ("the discrepancy is still present", an action kept open because an old copy said so). The person asked for a way
to tell an old version from the current one.

Rules:
- Group a folder's files into document families: the same name once version marks (v3, v3_1, v2.0), dates (2026-10-21,
  20261021) and words like FOR REVIEW, DRAFT, FINAL and ARCHIVE are taken out, within the same top folder. An Archive,
  Old or Superseded subfolder doesn't make a new family.
- The current copy is the highest date, then version, then modified time, among the family's files that still exist
  outside an Archive folder.
- A change to any other copy closes itself as "an older version; the current one is <file>", visible among the
  auto-closed changes with a way to bring it back. A copy in an Archive folder is never current.
- The current copy's change says which version it replaces, and the assistant's instructions say the newer version wins:
  record what it says now, write a correction when it contradicts an earlier fact, and never report a "discrepancy"
  against an older copy.
- The archive folder names and the words to ignore are settings.
- What it can't do: two versions with unrelated names aren't linked. Say so in the help, and let the person link two
  files by hand.

Tests:
- "<deck>_v3" and "<deck>_v3_1" are one family, and v3_1 is current;
- a copy moved into Archive closes itself;
- two documents that differ only by an id ("<form> 1234" and "<form> 5678") stay separate;
- a deleted file is never chosen as current.

## 2. Completing a project ends everything still open on it

The person's manager said a discovery project was complete (the direction was chosen; further work goes to next year's
backlog). The assistant moved the project to Completed and left its 26 actions, 3 risks and a dozen questions open, still
chasing people about them. The person had to send feedback to have them closed.

Rules:
- Completing a project winds it down in the same step: its open actions, its open risks and the questions filed about it
  are dropped, as one change the person can see and undo.
- Dropped, not done: nobody gets credit for work that didn't happen, no history row says "completed", and the "action for
  you" notices to other people are withdrawn.
- A `keep` list names anything that should outlive the project (a handover action, say). When the assistant isn't sure
  something should go, it asks once, listing what it would keep.
- The same applies when a project is archived or put on hold for good. Something only paused stays open, marked on hold.

Tests: completing a project with open actions, risks and questions leaves none open; their owners' notices are withdrawn;
an item in `keep` survives; undo brings everything back.

## 3. One failing step must never stop the background work

The assistant's change for (2) listed the same risk twice. The second removal failed, and the helper reported the failure
the way a command-line tool does: it exited. The background loop caught only ordinary errors, so the exit killed the
thread that applies changes, starts scheduled jobs and hands work to the assistant. The change stopped halfway (15 of 26
actions gone) and was never rolled back or sent back. The pages kept loading, so nothing looked wrong. For 25 minutes
nothing ran, including the person's next piece of feedback. The only health check was "the server answers", and it would
have taken an hour of missed scheduled checks to notice.

Rules:
- Library code never exits the process. It raises an error the caller handles. The applier treats any failure in a step,
  including an exit, as a failed change: roll back everything, record why, and send it back to the assistant to redo.
- Repeats are harmless: removing something an earlier step of the same change already removed is skipped, not an error.
- The background loop survives anything: each pass is guarded, a failure is logged and shown as an automation issue, and
  the next pass runs.
- A heartbeat, not just "the page answers": the loop writes a heartbeat every pass; the watchdog restarts the app when
  it's a few minutes old, even while the pages still load, and says so on the health card.
- Rehearse before touching real data: the repair of a half-applied change was tried on a copy of the data first. Build
  that in as "try this change on a copy" for anything large.

Tests:
- a step that exits leaves the data as it was and sends the change back;
- a change that removes the same item twice applies cleanly;
- a loop pass that throws doesn't stop the next one;
- a stopped loop with a working web server is restarted within minutes.

## 4. A meeting needs lead time on Today

On a Friday, Today's count left out "set up and hold the launch-planning meeting", due on Monday. Today counted only
meetings due "this week" (through the last working day), so Monday's meeting was invisible on the last working day it
could be set up.

Rules:
- A to-do that needs lead time is counted from when the work must start, not from its due date. A meeting the person sets
  up counts from a few working days before (a setting; two here), so on a Friday it shows Monday's and Tuesday's
  meetings.
- The line names the day when it's past the week: "Set up 1 meeting by Mon 10/26", not "this week".
- A meeting that's already sent shows only on its day, as "hold".
- The same lead time fits anything with a known runway: prep that needs a document, an invitation that needs a room.

Tests: on a Friday, a meeting due Monday is on Today; on a Wednesday, a meeting due next Wednesday isn't; one whose
invitation is out shows only on its day.
